# DDoS Attack Visualizer

## 1. Project Overview

This project is a real-time global DDoS attack visualization system.

The application displays attack activity as animated flows between countries on an interactive 3D globe.

The project combines:

* Cloudflare Radar aggregated DDoS telemetry
* FastAPI
* PostgreSQL / Supabase
* WebSockets
* Next.js
* TypeScript
* globe.gl
* Three.js

The primary goal is to demonstrate strong engineering through:

```text
External telemetry
        ↓
Data ingestion
        ↓
Normalization
        ↓
Weighted sampling
        ↓
Real-time event generation
        ↓
WebSocket streaming
        ↓
3D visualization
        ↓
Analytics / replay
```

This is a portfolio project.

The system must prioritize:

1. Correctness
2. Honest representation of data
3. Clean architecture
4. Maintainability
5. Performance
6. Good user experience

Do not add complexity merely to make the project appear more sophisticated.

# 7. Data Integrity Rule

This is one of the most important project rules.

The application must never present synthetic data as real telemetry.

There are two categories:

### Real telemetry

Derived from Cloudflare Radar.

```json
{
  "real": true,
  "source": "cloudflare_radar"
}
```

### Synthetic / representative traffic

Generated by our application.

```json
{
  "real": false,
  "source": "synthetic"
}
```

The frontend must visually distinguish these two categories.

Never fabricate telemetry values and present them as observed measurements.

For example, do NOT invent:

```text
3200 Mbps
```

unless the underlying data actually provides that measurement.

Use observed percentages/shares or derived visualization intensity instead.

---

# 8. Cloudflare Radar

Cloudflare Radar is the primary external data source.

The backend periodically retrieves:

* Layer 3 attack data
* Layer 7 attack data

Initial refresh interval:

```text
5 minutes
```

Do not poll the Cloudflare API for every generated WebSocket event.

The API data should be converted into a weighted probability distribution.

Example:

```text
RU → US    40%
CN → US    25%
CN → JP    15%
DE → US    10%
FR → GB    10%
```

The live event generator samples from this distribution.

---

# 9. Radar Client Responsibilities

The Radar client should:

1. Call Cloudflare Radar
2. Handle HTTP errors
3. Validate responses
4. Normalize the data
5. Convert country identifiers into the application's format
6. Return typed Python objects

The Radar client must NOT:

* broadcast WebSocket events
* manipulate frontend state
* contain database business logic
* generate synthetic attacks

Keep responsibilities separate.

---

# 10. Real Attack Event Generation

Real visualization events are sampled from the latest Radar distribution.

Process:

```text
Radar API
   ↓
normalized observations
   ↓
weighted distribution
   ↓
weighted random selection
   ↓
source/target country
   ↓
coordinate jitter
   ↓
visualization event
   ↓
WebSocket broadcast
```

The generated event represents a visualization sample based on the observed distribution.

It does NOT represent a specific packet, IP address, or individually observed attack.

---

# 11. Coordinate Handling

Cloudflare Radar provides aggregated country-level information.

The application therefore uses representative country coordinates.

Do not claim that a generated coordinate is the exact source or destination of an attack.

Coordinates should be jittered around country-level representative locations so that multiple events do not originate from exactly the same point.

---

# 12. Ambient Traffic

The application may generate synthetic background traffic.

Ambient traffic exists to improve visualization density and spatial context.

Ambient traffic must:

```json
{
  "real": false,
  "source": "synthetic"
}
```

Ambient traffic must be visually weaker than real telemetry.

Never allow ambient traffic to dominate the visualization.

---

# 13. Event Schema

The primary WebSocket attack event should follow this structure:

```json
{
  "type": "attack",
  "data": {
    "id": "uuid",
    "timestamp": 1723545600000,
    "real": true,
    "source": "cloudflare_radar",
    "sourceCountry": "RU",
    "sourceLat": 58.2,
    "sourceLng": 101.4,
    "targetCountry": "US",
    "targetLat": 41.0,
    "targetLng": -96.8,
    "layer": "L3",
    "attackType": "volumetric",
    "attackShare": 0.124
  }
}
```

Do not casually change this schema.

If a breaking change is necessary, update:

1. Backend schema
2. WebSocket documentation
3. Frontend types
4. Tests

in the same change.

```text

```

### Attack

```json

}
```

### Stats

```json
{
  "type": "stats",
  "data": {}
}
```

### System

```json
{
  "type": "system",
  "data": {}
}
```

The frontend must not guess message types.

Unknown message types should be safely ignored or logged.

# 15. WebSocket Connection Manager

The backend must maintain a central connection manager.

Responsibilities:

```text
connect()
disconnect()
broadcast()
```

The manager should:

* track active connections
* broadcast events
* remove disconnected clients
* handle failed sends
* support heartbeat behavior

Do not duplicate WebSocket connection-management logic across multiple modules.

---

# 16. WebSocket Heartbeat

Use a heartbeat mechanism.

Initial target:

```text
30 seconds
```

Dead connections should be removed.

The backend must not retain closed client connections indefinitely.

# 24. Error Handling

External API failures must not crash the entire application.

If Cloudflare Radar temporarily fails:

```text
Radar failure
     ↓
log error
     ↓
retain previous valid distribution
     ↓
continue streaming
```

Do not replace valid previous data with an empty distribution merely because one API request failed.

If no Radar data has ever been loaded, synthetic fallback traffic may be used.

Synthetic fallback must remain:

```text
real = false
```

# 26. Performance

The frontend may render hundreds of events.

The backend should therefore use a bounded live event system.

Do not allow unlimited in-memory event growth.

Use a configurable maximum:

```text
MAX_LIVE_EVENTS=500
```

Expired visualization events should be removed.

The backend should not retain every event forever.

---

# 27. Frontend Performance

The frontend should avoid creating unnecessary React components for every individual attack arc.

The globe visualization should be handled efficiently through globe.gl / Three.js.

The event stream should use bounded state.

Do not continuously append to an infinite array.

Use a rolling window.

# 43. Current Goal

The immediate goal is NOT to build the complete website.

The immediate goal is:

```text
Supabase
   ↓
FastAPI
   ↓
Cloudflare Radar
   ↓
normalized data
   ↓
weighted distribution
   ↓
WebSocket
   ↓
one valid attack event
```

Once that pipeline works reliably, the frontend can consume it.

The first milestone is therefore:

> **Connect to Cloudflare Radar, normalize the data, store the observation in PostgreSQL, generate a valid event from the distribution, and broadcast it through WebSocket.**

Everything else is built on top of this foundation.
